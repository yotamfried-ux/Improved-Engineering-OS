# Pre-implementation research inventory

Verified on 2026-09-04. Scope: documentation research only. No product feature, dependency installation, agent trial, infrastructure provisioning, or Stage 0 gate was executed.

## Source of truth and project scope

Read the complete [37-page architecture report](../source/Improved-Engineering-OS_Architecture_Report.pdf) and [frozen build guide 1.4.1](../source/Improved-Engineering-OS-Build-Guide-FROZEN-v1.4.1.md). The architecture constitution and the guide's explicit refinements remain the design baseline; this inventory records external evidence and proposed implementation checks, not amendments or owner acceptance of D18–D36.

The project is a personal engineering knowledge and evidence system with an agent-neutral core. Canonical code, admitted knowledge, controls, and release intent live in Git; project intent lives in target repositories; local runtime state and queued events live locally; observations, candidates, telemetry, and derived evidence live in managed Supabase. Agents retain control of task execution. The four-tool interface is `resolve`, `inspect`, `expand`, and `observe`.

The immediate sequence is minimal contracts and harness → source runtime → 10–20 seed assets and minimal evidence/telemetry → Stage 3 real-agent slice. Later work includes immutable releases, broader import, profiles, assurance, learning/promotion, ecosystem discovery, and real-project qualification. The guide requires Stage 3 to pass before Stage 4+ implementation. Existing knowledge is reusable; the old orchestration/runtime is not the new foundation.

## Research method and confidence

Sources below were opened on the publisher's documentation domain or the project's public upstream GitHub repository. Company examples are first-party engineering accounts. Repository relevance was checked against its README, documentation, source layout, and published license information; stars and marketing performance claims were not treated as qualification evidence.

“Verified” here means the source was retrieved and supports the stated fact or available component. No listed library was installed, benchmarked, security-audited, or proven compatible with IEOS. Default-branch links are discovery references: record an exact package version or commit and its license/NOTICE files before any reuse. Some individual deep links failed retrieval; the successful canonical pages linked below are the retained references.

## 4. Findings that change the implementation checklist

| ID | Evidence and source location | Recommended treatment before affected code |
|---|---|---|
| R1 — MCP package identity | Guide D18.5 names `@modelcontextprotocol/sdk`; the [current upstream](https://github.com/modelcontextprotocol/typescript-sdk) identifies stable v2 as `@modelcontextprotocol/server` and `@modelcontextprotocol/client`, implementing the required July 2026 spec. | Record the actual package coordinates, exact versions and license notices in the Stage 0 dependency decision. Prove required protocol behavior at Stage 1. The protocol choice is supported; the old package name should not be copied blindly. |
| R2 — JCS versus normalization | Guide D35 says NFC normalization for strings. [RFC 8785 §3.1](https://www.rfc-editor.org/rfc/rfc8785.txt) requires Unicode strings to be preserved during JCS processing; §3.2.3 sorts JSON keys by UTF-16 code units. The guide separately sorts file-manifest entries by UTF-8 path bytes. | Make IEOS normalization, collision rejection, and filename handling explicit before canonicalization. Keep RFC behavior intact and distinguish the two ordering rules. Cover decomposed/composed strings, key collisions and non-BMP characters with fixtures. This is an interpretation to confirm through Stage 0 findings, not a silent source edit. |
| R3 — WAL engine version | [SQLite WAL §11](https://sqlite.org/wal.html) documents a rare concurrent write/checkpoint corruption bug fixed in 3.51.3 and later, with selected backports. D26 uses concurrent WAL writers. | Verify the SQLite engine bundled by the chosen better-sqlite3 release contains the fix. Record `sqlite_version()` in qualification. Also account for busy responses, checkpoint behavior and local-only storage. |
| R4 — Node availability | Guide D18.1 infers Node availability from the agents. [Codex upstream](https://github.com/openai/codex) provides standalone native binaries; the local executable is native too. | Keep Node 24 as the proposed IEOS runtime, but check/install it explicitly in setup and `doctor`. Agent installation is not evidence that the required Node runtime exists. |
| R5 — sandbox claims | Guide Stage 0 asks for fresh temporary directories and no inherited environment. [Inspect's sandbox documentation](https://inspect.aisi.org.uk/sandboxing.html) distinguishes container network restrictions from host-side tools, model calls and graders. | Define actual filesystem/network/process boundaries. A fresh directory or SDK settings isolation alone does not prove that an agent cannot read evaluator files. Test isolation before accepting the Stage 3 results. |
| R6 — verification boundary | [Supabase](https://supabase.com/docs/guides/functions/auth) leaves authentication to custom handlers when checks are disabled; [GitHub](https://cli.github.com/manual/gh_release_verify-asset) distinguishes local asset verification from release verification. | Write negative tests against the actual boundary, not merely configuration flags or attestation presence. Applies at Stage 2 and Stage 4 respectively. |

No numeric score weights, promotion margins, trial budgets, or release thresholds were invented. The guide's open-parameter register remains open. Likewise, F1's “core imports nothing outside itself” needs reconciliation with its prescribed Zod schemas and any proposed JCS dependency during Stage 0; this inventory does not relax the fitness rule.

## 5. Concise next research tracks

1. **Stage 0 compatibility and contracts:** select exact toolchain/schema/test/JCS/MCP versions; resolve R1/R2 and F1 dependency wording in a short decision record. Produce a version-and-compatibility matrix plus fixture requirements.
2. **Stage 0–3 harness:** compare Inspect and mini-swe-agent components with a minimal TypeScript harness; confirm the primary agent, execution identity, budget and isolation mechanism. Produce the three-task slice manifest outline and grader controls.
3. **Stage 1–2 storage and ingest:** verify SQLite binary/platform compatibility, deterministic FTS build strategy and token/RPC authorization against current Supabase docs. Produce a failure matrix for duplicate delivery, outage, kill, revocation and incomplete runs.
4. **Knowledge reuse:** inventory the old Engineering-OS corpus at a known revision using guide Appendix A; identify 10–20 seed candidates and provenance, with no legacy runtime import. Compare only the relevant Backstage descriptor patterns.
5. **Later stages:** retain Netflix/OTel references for evidence lineage and Google/GitHub/Sigstore references for rollout and verification; defer implementation and detailed evaluation until their stages.

Research is reported here before implementation. Next product work requires a new instruction to begin; this inventory is not a claim that Stage 0 or any later gate passed.
